# Spotlight shadow research and design record

This research informed PulseForge's bounded Vulkan spotlight-shadow implementation. References are pinned to the upstream revisions observed during the Phase D work; no third-party implementation code was copied.

## Source-grounded comparison

| Topic | Hazel | Godot | Filament | bgfx / Khronos | PulseForge decision |
|---|---|---|---|---|---|
| Shadow pass architecture | Public Hazel shows renderer/editor abstractions, but no public 3D PBR spotlight-shadow renderer. | RenderingServer separates light authoring from renderer storage; RD renderer owns positional shadow-atlas work. | `ShadowMap` constructs light cameras and per-shadow parameters; the manager owns selection/resources. | bgfx examples show explicit view/render-target passes; Vulkan requires depth attachment writes to become shader reads through ordered transitions. | Keep renderer-owned passes and resources in `SceneRenderer`; no scene/backend handles. |
| Spotlight projection | Not available in public Hazel code inspected. | Spot shadow uses a perspective projection; editor warns when the angle is too wide for shadows. | `ShadowMap::updateSpot` routes spot outer angle and near/far to punctual projection. | Standard perspective depth map. | RH perspective, FOV `2 * outer half-angle`, local world `-Z`, near 0.05, far authored range, Vulkan ZO depth. |
| Shadow texture/resource allocation | Public Hazel framebuffer abstractions are not evidence of 3D spot map policy. | Configurable positional shadow atlas and quadrant subdivision. | Shadow manager budgets and manages per-light shadow records; options expose map size and filtering. | Render-target and sampler explicit; Vulkan usage/layout are explicit backend concerns. | Four lazily created, fixed 1024² D32 maps, about 16 MiB, no atlas allocator. |
| Light-to-shadow assignment | No public 3D implementation found. | Renderer maps light instances into atlas regions and stores spot atlas rects for shader lookup. | Shadow records carry light identity, shadow index, type and face; shadow caster limits are explicit. | Not a direct local-light allocation reference. | UUID owners remain stable where eligible; selected lights use deterministic relevance ordering; overflow keeps direct illumination unshadowed. |
| Bias/filtering | Not present in public 3D source inspected. | Exposes bias/normal bias and shadow quality; engine supports selectable positional filtering. | `ShadowOptions` exposes map size and bias/filter choices; filtering complexity exceeds this milestone. | Vulkan depth compare/sampling synchronization is documented. | Fixed bounded raster bias; authorable normalized receiver depth bias, world-unit normal bias, manual 3×3 PCF with texel radius. |
| Editor controls | Public Hazelnut demonstrates component-oriented editor workflows, but no applicable public spot-shadow controls. | `Light3D` exposes shadow toggles and properties; light gizmos/configuration warnings are editor-side. | Light API has per-light cast-shadow and shadow options. | — | Inspector exposes only implemented cast, bias, normal-bias, softness controls; no point-shadow checkbox or fake resolution control. |
| Point-shadow extension | No public Hazel point-shadow renderer identified. | Omni shadows use six cube faces or dual-paraboloid modes; spot needs one map. | Current source includes point-face view construction and punctual update, but this is not adopted as a reason to expand Phase D. | Cube/cube-array renderability must be verified against NVRHI/backend resource capabilities. | Future proposal: six reusable 90° faces per point light or cube array only after NVRHI depth-face attachment and sampling contracts are proven. Not implemented now. |

## Hazel (highest-priority architectural reference)

- Repository: [TheCherno/Hazel](https://github.com/TheCherno/Hazel), observed public `master` revision `1feb70572fa87fa1c4ba784a2cfeada5b4a500db`.
- Inspected public files: [`Hazel/src/Hazel/Renderer/Renderer2D.h`](https://github.com/TheCherno/Hazel/blob/1feb70572fa87fa1c4ba784a2cfeada5b4a500db/Hazel/src/Hazel/Renderer/Renderer2D.h), [`Hazelnut/src/EditorLayer.cpp`](https://github.com/TheCherno/Hazel/blob/1feb70572fa87fa1c4ba784a2cfeada5b4a500db/Hazelnut/src/EditorLayer.cpp), and the public [README](https://github.com/TheCherno/Hazel/blob/1feb70572fa87fa1c4ba784a2cfeada5b4a500db/README.md).
- The public README describes the repository as early-stage, lists high-fidelity PBR 3D rendering among future features, and explicitly says a more advanced `Hazel-dev` repository is private. Therefore Hazel's private/newer 3D light and shadow implementation was not inspected and is not cited as evidence.
- Useful public principles are the renderer-facing submission boundary and editor framebuffer/scene workflow. They support keeping PulseForge's editor-facing authoring separate from `SceneRenderer` GPU ownership, but provide no spotlight-shadow algorithm to adopt.
- Hazel repository license is Hazel's included license. No Hazel code was copied.

## Godot

- Repository: [godotengine/godot](https://github.com/godotengine/godot), observed `master` revision `232e6b14abf6e590b41d60f11704e42de22bff72` (MIT license).
- Files inspected: [`scene/3d/light_3d.cpp`](https://github.com/godotengine/godot/blob/232e6b14abf6e590b41d60f11704e42de22bff72/scene/3d/light_3d.cpp), [`servers/rendering/rendering_server.h`](https://github.com/godotengine/godot/blob/232e6b14abf6e590b41d60f11704e42de22bff72/servers/rendering/rendering_server.h), [`servers/rendering/renderer_rd/shaders/scene_forward_lights_inc.glsl`](https://github.com/godotengine/godot/blob/232e6b14abf6e590b41d60f11704e42de22bff72/servers/rendering/renderer_rd/shaders/scene_forward_lights_inc.glsl), and [official lights/shadows documentation](https://docs.godotengine.org/en/stable/tutorials/3d/lights_and_shadows.html).
- The public API separates light shadow controls and atlas management from scene-node authoring. The forward shader uses spot light-space coordinates and atlas rectangles. Official docs state that a spot needs one shadow texture while an omni shadow needs six faces (or two dual-paraboloid passes), and warn that wide spots lose useful shadow quality and stop shadowing around 89 degrees.
- The atlas is an intentional scalability/packing mechanism, but it is more machinery than PulseForge's four-shadow budget needs. PulseForge adopts an explicit width limit and one-map-per-selected-light model, not Godot's server/atlas architecture.

## Filament

- Repository: [google/filament](https://github.com/google/filament), observed `main` revision `764fe6cac9bdb4ba24d3d852344dfa04a5f70f75` (Apache-2.0).
- Files inspected: [`filament/include/filament/LightManager.h`](https://github.com/google/filament/blob/764fe6cac9bdb4ba24d3d852344dfa04a5f70f75/filament/include/filament/LightManager.h), [`filament/src/ShadowMap.cpp`](https://github.com/google/filament/blob/764fe6cac9bdb4ba24d3d852344dfa04a5f70f75/filament/src/ShadowMap.cpp), and [`filament/src/ShadowMapManager.cpp`](https://github.com/google/filament/blob/764fe6cac9bdb4ba24d3d852344dfa04a5f70f75/filament/src/ShadowMapManager.cpp).
- `LightManager` documents spot cone/range and per-light shadow options (1024 default map size). `ShadowMap::updateSpot` passes the spot outer cone and near/far into punctual projection. The source also contains point-face handling, illustrating that omnidirectional point shadows require a separate face-oriented path; this does not make that path part of Phase D.
- Adopted: separate emission data from shadow visibility, explicit map budgeting, and shadow camera construction from light parameters. Rejected: importing the full shadow manager, clustered renderer, or advanced filtering/resource policy.

## bgfx and Khronos/Vulkan

- bgfx repository: [bkaradzic/bgfx](https://github.com/bkaradzic/bgfx), observed revision `8f451e9102b1845b29dfe500116611ad283632ec` (BSD 2-Clause). The inspected [`examples/31-rsm/reflectiveshadowmap.cpp`](https://github.com/bkaradzic/bgfx/blob/8f451e9102b1845b29dfe500116611ad283632ec/examples/31-rsm/reflectiveshadowmap.cpp) is a reflective directional shadow-map example, not a spotlight algorithm. It demonstrates explicit shadow render-target and sampler lifecycle and is used only as a general pass-organization reference.
- Khronos [Vulkan depth guide](https://github.com/KhronosGroup/Vulkan-Guide/blob/main/chapters/depth.adoc) and [synchronization examples](https://docs.vulkan.org/guide/latest/synchronization_examples.html) describe depth attachment usage and the write-to-shader-read ordering required between a depth pass and sampling. PulseForge relies on the NVRHI backend's existing shader-readable depth target state transitions, verified by the GPU scenario under validation.
- No code from these examples was copied. No dependency was added.

## PulseForge design decision

PulseForge already has persistent shader-readable D32 directional maps, a depth-only indexed mesh pass, an NVRHI `RenderTargetFrameScope`, Vulkan zero-to-one projection conventions, and manual PCF. The least disruptive solution is to extend the shared `SceneRenderer`: independently select up to four shadow-eligible spots from the already-selected 32 local lights, retain UUID-to-slot ownership while eligible, render those maps before the main HDR pass, and store the slot only on the matching spot's existing local-light GPU record. Shadow visibility multiplies only that spot's direct BRDF result. Existing scenes remain unshadowed by default. Point-light shadows are a later design, not a runtime placeholder.

## Future point-light shadow design (not implemented)

The lowest-risk first point-shadow prototype would use a bounded fixed number of point lights, each with six persistent D32 face targets and six 90-degree views (36 depth-only caster passes at a six-light budget, before culling). A comparison-sampled depth cubemap/cube array could reduce target/binding bookkeeping, but must first be proven through NVRHI's array-slice framebuffer API, cube compatible sampled views, format capabilities, and backend synchronization. Six independent 2D maps are compatible with PulseForge's current render-target abstraction and easiest to validate, at a cost of six times one spotlight's storage and draw work per point light. A shared atlas is not recommended until measured occupancy makes this fixed budget inadequate. Keep point shadow identity/index separate from the existing 32-light selection, use stable entity IDs, and budget spot/point shadow passes jointly so one local light's visibility never applies to another. Validate face orientation/seams and PCF across cube edges before exposing authoring controls.
