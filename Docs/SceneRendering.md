# Scene Rendering

`SceneRenderSnapshotBuilder` converts a scene, a selected camera, and a framebuffer aspect ratio into immutable per-frame render data. Callers may select a camera entity explicitly or let the builder resolve the scene's sole camera marked `primary`; missing or multiple primary cameras produce clear errors. `BuildForView` accepts a view-projection matrix and explicit world position for transient views such as the editor camera; its snapshot has no camera entity. The snapshot includes at most one authored directional light and one environment light. Environment orientation is composed from entity hierarchy rotations (`parentWorld * local`), ignoring translation and scale. The builder performs no GPU work.

Camera projection uses a right-handed, zero-to-one depth range with camera-up in positive clip-space Y. NVRHI's Vulkan backend maps positive clip-space Y to the framebuffer top through its negative-height Vulkan viewport. The editor uses that same mapping for gizmo projection and picking; its displayed offscreen image keeps the default top-left-to-bottom-right UV orientation.

`SceneRenderer` consumes that snapshot through PulseForge's renderer and asset-cache APIs. Call `PrepareScene` during `Layer::OnUpdate`, before `Application` opens the frame command list; it resolves meshes and PBR material textures, processes/caches any HDR environment, and lazily creates compatible pipelines. Call `RenderPreparedScene` from `Layer::OnRender` to update frame/object constants and submit the environment background and indexed geometry draws. The overload taking a `RenderTarget` begins and clears that target, submits the same prepared scene using pipelines for its color format, then ends the target. With SSAO enabled, the renderer also performs a full-resolution view-normal/depth prepass followed by half-resolution AO and separable bilateral filtering before forward shading. Its auxiliary targets persist and resize to the actual scene target. The application and project must outlive the renderer, and the project must not be moved while the renderer exists because asset caches refer to its registry.

The scene path uses opaque Cook-Torrance metallic/roughness shading (GGX distribution, Smith geometry, Schlick Fresnel) with one authored directional light plus optional HDR image-based lighting. Directional direct light is shadowed by four persistent, camera-relative 1024x1024 D32 cascades, rendered with depth-only pipelines and no color attachment. Splits use a fixed practical distribution (65% logarithmic, 35% uniform); the light-space square fit is snapped to shadow texels and expanded by 10% (at least two world units) for nearby off-frustum casters, with a 50-world-unit caster-depth margin. A 3x3 PCF filter has an authorable radius in shadow texels and adjacent cascades blend over the final 8% of each interval. Beyond the authored shadow distance, direct light is unshadowed. Shadow visibility affects only direct light, never IBL. All opaque meshes currently cast and receive; each mesh is submitted to every cascade without spatial caster culling. Bias combines the NVRHI raster constant bias (rounded to an integer), a fixed slope-scaled raster bias, and a small normal-scaled receiver offset. These first-generation trade-offs can be tuned in the Directional Light Inspector to balance acne against detached shadows.

Transient callers must provide separate view and projection matrices plus near/far clips to enable cascades. The legacy view-projection-only overload remains available for compatibility but intentionally renders its directional light unshadowed because that matrix cannot define the camera frustum reliably.

Without an environment, no directional light still renders black. The environment adds diffuse irradiance and split-sum specular IBL and draws its HDR background behind geometry. Light color, HDR environment, and material factors are linear; base-color texture samples are decoded by the sRGB texture format. Light rays travel along the owning entity's transformed local -Z axis; the BRDF uses the negated vector as surface-to-light. Entity scale is part of that direction transform. Normal matrices use inverse-transpose and singular model transforms are rejected for drawing. Missing glTF normals are area-weighted and averaged over shared vertices; degenerate faces add no contribution and vertices with no valid contribution fall back to +Z. Offscreen scene rendering currently requires the Vulkan backend; the transitional OpenGL backend continues to provide its bootstrap/ImGui path and does not render scene snapshots. The renderer supports one canonical vertex layout per instance.

SSAO uses a deterministic 32-sample view-space hemisphere kernel with a stable screen-space hash rotation, a 0.65-unit radius, 0.025 depth bias, and 1.15 strength by default. The full-resolution prepass stores encoded view-space normals in RGBA8_UNorm and sampleable D32 depth; raw AO and horizontal/vertical 5-tap bilateral passes run at ceil-half resolution. Filtering weights account for view-depth and normal differences to limit silhouette bleeding. AO modulates diffuse IBL, while a conservative roughness/view-dependent specular-occlusion approximation attenuates indirect specular; direct lighting, directional shadows, and the HDRI background are not occluded. The renderer exposes a small `AmbientOcclusionSettings` API for disabling/tuning this first implementation, but settings are renderer-owned and are not serialized. SSAO remains screen-space: off-screen occluders, thin geometry, view-dependent disappearance, and lack of temporal accumulation or multi-bounce occlusion are expected limitations.

Renderer textures describe 2D or cube dimensions, RGBA16F/RGBA32F floating-point color, mip levels, and explicit per-mip/per-face uploads. Cube array slices have stable `+X, -X, +Y, -Y, +Z, -Z` ordering. Environment preprocessing is CPU-based and cached by asset UUID with bounded output sizes. The Vulkan renderer accepts RGBA16F offscreen color targets as a foundation for future HDR scene rendering; the visible scene output remains LDR and HDR radiance can still clip. No exposure or tonemapping is implemented. RGBA16F target creation checks the active device's optimal-tiling sampled-image and color-attachment features required by the requested usage. This has been exercised on an AMD Radeon RX 9070 XT (driver 26.6.4); support remains device-specific. HDR framebuffer integration and tonemapping remain deferred.

An opt-in GPU regression executable is available with `-DPULSEFORGE_BUILD_GPU_VALIDATION_TESTS=ON` when a Vulkan renderer configuration is enabled. For example:

```powershell
cmake -S . -B Build/CMake/VS2022-x64 -G "Visual Studio 17 2022" -A x64 -DBUILD_TESTING=ON -DPULSEFORGE_BUILD_GPU_VALIDATION_TESTS=ON
cmake --build Build/CMake/VS2022-x64 --target PulseForgeGpuValidation --config Debug --parallel 1
.\Build\CMake\VS2022-x64\Debug\PulseForgeGpuValidation.exe
```

Run it from a logged-in Windows desktop session. It creates a small RGBA16F color+depth target, draws a scene-linear value with a matching pipeline, samples the target into the swapchain, and exits after three completed render/sample frames. The test exercises GPU commands and resource transitions but does not read back pixels to compare exact values. Khronos validation and NVRHI validation are enabled automatically in Debug when available. This executable is intentionally not registered with default CTest, so CPU-only test runs do not require a Vulkan device or display.
