# Scene Rendering

`SceneRenderSnapshotBuilder` converts a scene, a selected camera, and a framebuffer aspect ratio into immutable per-frame render data. Callers may select a camera entity explicitly or let the builder resolve the scene's sole camera marked `primary`; missing or multiple primary cameras produce clear errors. `BuildForView` accepts a view-projection matrix and explicit world position for transient views such as the editor camera; its snapshot has no camera entity. The snapshot includes at most one authored directional light and one environment light. Environment orientation is composed from entity hierarchy rotations (`parentWorld * local`), ignoring translation and scale. The builder performs no GPU work.

Camera projection uses a right-handed, zero-to-one depth range with camera-up in positive clip-space Y. NVRHI's Vulkan backend maps positive clip-space Y to the framebuffer top through its negative-height Vulkan viewport. The editor uses that same mapping for gizmo projection and picking; its displayed offscreen image keeps the default top-left-to-bottom-right UV orientation.

`SceneRenderer` consumes that snapshot through PulseForge's renderer and asset-cache APIs. Call `PrepareScene` during `Layer::OnUpdate`, before `Application` opens the frame command list; it resolves meshes and PBR material textures, processes/caches any HDR environment, and lazily creates compatible pipelines. Call `RenderPreparedScene` from `Layer::OnRender` to update frame/object constants and submit the environment background and indexed geometry draws. The overload taking a `RenderTarget` begins and clears that target, submits the same prepared scene using pipelines for its color format, then ends the target. With SSAO enabled, the renderer also performs a full-resolution view-normal/depth prepass followed by half-resolution AO and separable bilateral filtering before forward shading. Its auxiliary targets persist and resize to the actual scene target. The application and project must outlive the renderer, and the project must not be moved while the renderer exists because asset caches refer to its registry.

`RenderPreparedSceneToHdr(width, height)` renders the prepared scene into the renderer-owned persistent `RGBA16_Float` color + `Depth32Float` target. Call it only from `Layer::OnRender`, after successful `PrepareScene` and while an application frame is active. It performs shadow cascades and SSAO before opening the HDR target, then submits the environment background and opaque PBR meshes with RGBA16F-compatible pipelines. The target is cleared to scene-linear black with depth 1.0; its color attachment becomes shader-readable when the target ends. The result contains borrowed color/depth pointers, extent, draw count, and background status. `TargetGeneration` identifies successful target replacements: it increments only after a new compatible target is published, not on reuse or failed replacement. Borrowed pointers and bindings are valid until resize or renderer destruction; consumers must rebuild bindings when the generation changes.

`SceneRenderer::RenderPreparedSceneToOutput()` is the visible HDR-to-SDR route. It renders geometry exactly once into the persistent HDR target, then draws a fullscreen triangle that samples HDR and writes the selected output. The overload taking an existing SDR `RenderTarget` supports the editor's sRGB viewport; the no-argument overload writes to the current swapchain for the standalone game. Both execute inside the active application frame after `PrepareScene`. The `SceneRenderer` owns the HDR target, fullscreen buffer, shader/pipeline variants, sampler, constant buffer, and generation-tracked HDR binding. Repeated frames reuse resources; target resize replaces the HDR target and invalidates the old binding. The legacy `RenderPreparedScene()` routes remain available for explicit LDR rendering.

`ToneMappingSettings::ExposureEV` defaults to 0 EV and accepts finite values from -16 through +16 stops. Exposure is `exp2(EV)` and applies to scene radiance only; settings are transient per `SceneRenderer`, are not serialized, persist across Edit/Play while that renderer is retained, and reset when it is recreated. The final pass uses the Narkowicz-style ACES-fitted approximation `saturate((x*(2.51*x+0.03))/(x*(2.43*x+0.59)+0.14))`; this is not the complete Academy ACES color-management system. HDR scene values are not gamma encoded or clamped to [0,1] before this curve. Negative/NaN channels map to black; positive infinity maps to white rather than propagating NaNs to the SDR target.

For an sRGB destination attachment, the shader writes display-linear tone-mapped values and the attachment performs sRGB encoding. For an UNORM destination it explicitly applies the piecewise linear-to-sRGB transfer function. Vulkan prefers supported sRGB swapchain formats before UNORM while retaining UNORM fallbacks. The editor tonemaps its scene into the existing sRGB viewport target and then composes ImGui afterward. On an sRGB swapchain, ImGui draws directly to that attachment. On a UNORM swapchain, ImGui draws into a persistent, size-matched `RGBA8_Srgb` target with no depth attachment, so sRGB texture samples and linearized UI vertex colors are blended in linear light; the completed opaque sRGB image is sampled and encoded once into the UNORM swapchain by a fullscreen output-transfer pass. This pass does not apply scene exposure or tonemapping. The intermediate is recreated only when the framebuffer extent changes and its sampling binding is replaced with it. Exposure therefore does not affect editor UI. The editor's compact Scene Viewport `Exposure (EV)` control is transient and does not dirty the scene.

The HDR target is one RGBA16F+D32 allocation, approximately 12 bytes per pixel before driver overhead (about 23.7 MiB at 1920x1080 and 42.2 MiB at 2560x1440). The current visible editor and game paths now use HDR rendering followed by SDR tonemapping; HDR10/PQ/HLG, automatic exposure, and OpenGL scene rendering remain unsupported. GPU validator modes `--scene-hdr` and `--scene-tonemap` exercise actual scene draws, target reuse/resize, exposure variants, HDR sampling, and sRGB/UNORM SDR targets. These tests validate GPU command/resource behavior but do not read back pixels; exact stored radiance and subjective visual quality still require the manual checks described below.

The scene path uses opaque Cook-Torrance metallic/roughness shading (GGX distribution, Smith geometry, Schlick Fresnel) with one authored directional light plus optional HDR image-based lighting. Directional direct light is shadowed by four persistent, camera-relative 1024x1024 D32 cascades, rendered with depth-only pipelines and no color attachment. Splits use a fixed practical distribution (65% logarithmic, 35% uniform); the light-space square fit is snapped to shadow texels and expanded by 10% (at least two world units) for nearby off-frustum casters, with a 50-world-unit caster-depth margin. A 3x3 PCF filter has an authorable radius in shadow texels and adjacent cascades blend over the final 8% of each interval. Beyond the authored shadow distance, direct light is unshadowed. Shadow visibility affects only direct light, never IBL. All opaque meshes currently cast and receive; each mesh is submitted to every cascade without spatial caster culling. Bias combines the NVRHI raster constant bias (rounded to an integer), a fixed slope-scaled raster bias, and a small normal-scaled receiver offset. These first-generation trade-offs can be tuned in the Directional Light Inspector to balance acne against detached shadows.

Transient callers must provide separate view and projection matrices plus near/far clips to enable cascades. The legacy view-projection-only overload remains available for compatibility but intentionally renders its directional light unshadowed because that matrix cannot define the camera frustum reliably.

Without an environment, no directional light still renders black. The environment adds diffuse irradiance and split-sum specular IBL and draws its HDR background behind geometry. Light color, HDR environment, and material factors are linear; base-color texture samples are decoded by the sRGB texture format. Light rays travel along the owning entity's transformed local -Z axis; the BRDF uses the negated vector as surface-to-light. Entity scale is part of that direction transform. Normal matrices use inverse-transpose and singular model transforms are rejected for drawing. Missing glTF normals are area-weighted and averaged over shared vertices; degenerate faces add no contribution and vertices with no valid contribution fall back to +Z. Offscreen scene rendering currently requires the Vulkan backend; the transitional OpenGL backend continues to provide its bootstrap/ImGui path and does not render scene snapshots. The renderer supports one canonical vertex layout per instance.

SSAO uses a deterministic 32-sample view-space hemisphere kernel with a stable screen-space hash rotation, a 0.65-unit radius, 0.025 depth bias, and 1.15 strength by default. The full-resolution prepass stores encoded view-space normals in RGBA8_UNorm and sampleable D32 depth; raw AO and horizontal/vertical 5-tap bilateral passes run at ceil-half resolution. Filtering weights account for view-depth and normal differences to limit silhouette bleeding. AO modulates diffuse IBL, while a conservative roughness/view-dependent specular-occlusion approximation attenuates indirect specular; direct lighting, directional shadows, and the HDRI background are not occluded. The renderer exposes a small `AmbientOcclusionSettings` API for disabling/tuning this first implementation, but settings are renderer-owned and are not serialized. SSAO remains screen-space: off-screen occluders, thin geometry, view-dependent disappearance, and lack of temporal accumulation or multi-bounce occlusion are expected limitations.

Renderer textures describe 2D or cube dimensions, RGBA16F/RGBA32F floating-point color, mip levels, and explicit per-mip/per-face uploads. Cube array slices have stable `+X, -X, +Y, -Y, +Z, -Z` ordering. Environment preprocessing is CPU-based and cached by asset UUID with bounded output sizes. The Vulkan renderer checks active-device optimal-tiling sampled-image and color-attachment support when creating RGBA16F resources. HDR scene rendering and SDR tonemapping are now integrated in the visible Vulkan editor/game paths; support remains device-specific. The transitional OpenGL shell still does not render scene snapshots.

Point and spot lights add unshadowed local direct illumination to the same forward metallic/roughness BRDF. A `SceneRenderSnapshot` stores UUID-ordered, validated world-space lights; points use the world origin of their entity and spots use hierarchy-composed world rotation applied to local `-Z`. Entity scale affects position through the transform hierarchy but does not scale light range or direction. One entity may carry either or both local-light components. Moving a light is reflected by the next `PrepareScene`; it does not rebuild pipelines, HDRI resources, or directional shadow maps.

The Vulkan forward shader accepts up to 32 combined active point and spot lights in a persistent, 16-byte-aligned, 2,064-byte frame-lighting constant buffer. Zero-intensity lights are omitted. If more than 32 are active, the renderer deterministically keeps the most camera-relevant lights, scoring intensity, maximum color channel, range, and distance outside range; UUID and light type break ties. An overflow warning is emitted once per `SceneRenderer`. This bounded per-fragment loop suits small scenes, not an unlimited-light solution; Forward+/clustered assignment is a future scaling option.

Local-light RGB is authored in linear space and intensity is a unitless radiance multiplier, not calibrated candela or lux. Defaults are white point color, intensity 10, range 10; spots default to intensity 25, range 15, and 15/25-degree cone half-angles. Validation accepts intensity `[0, 1,000,000]`, range `(0, 10,000]` world units, finite nonnegative RGB, and spot half-angles `0.5 <= inner < outer <= 89.5` degrees. Point attenuation is a regularized inverse-square term multiplied by a smooth range window: `max(1 - (distance/range)^4, 0)^2 / max(distance^2, 0.01)`, and is zero at or beyond range. Spotlights multiply this by a smooth cosine-domain transition between inner and outer cone half-angles; angles are stored in degrees and converted to cosines for the GPU. Up to four selected spotlights can additionally cast shadows; point lights independently support up to two shadow owners. Each shadow visibility factor multiplies only its matching local light's direct BRDF contribution. Directional CSM remains separate and only attenuates directional direct light. IBL, SSAO, HDR accumulation, exposure, and tonemapping remain on their existing paths. GPU validator mode `--scene-local-lights` prepares bundled PBR geometry with environment and directional lighting, adds 32 points and two spots to exercise the 32-light budget/overflow policy, changes active light counts and transforms across frames, and exercises the real scene-to-HDR-to-SDR draw path. Its draw/resource checks do not read pixels, so visual contribution is not asserted numerically.

## Spotlight shadows

Spotlight shadows use four lazy, persistent 1024x1024 shader-readable D32 depth targets (about 16 MiB total), owned by `SceneRenderer` and reused across frames and scenes. The active-light budget remains 32 combined point/spot lights; at most four of the camera-relevant selected spots can own maps. Eligible existing owners keep their slots; new owners fill free slots in the deterministic local-light relevance order (UUID/type tie-breaks). A selected shadow-requesting spotlight over budget, with a zero intensity, no opaque casters, an invalid projection, or an outer cone half-angle above 80 degrees remains illuminated but unshadowed. Old scenes default `castShadows` to false. Shadow resources are allocated only after an eligible request is prepared; all mesh instances are rendered into each assigned map before the HDR PBR pass.

The light camera follows world position and the hierarchy-composed local `-Z` direction. Its right-handed perspective projection uses `2 * outerConeHalfAngle` vertical FOV, 0.05 world-unit near plane, the authored range as far plane, and Vulkan zero-to-one depth. Spot cones wider than 80 degrees retain their original lighting cone but do not cast shadows, avoiding unstable near-180-degree perspective matrices. The Inspector's `Shadow Bias` is a normalized light-space receiver-depth offset (0–0.02), `Shadow Normal Bias` is a world-unit normal offset (0–1), and `Shadow Softness` is the radius in shadow-map texels (0–4) for manual 3x3 PCF. Shadow targets and bindings are independent of the four directional CSM targets; a separate descriptor set uses register space 3. There is no atlas, per-light resolution control, caster-frustum culling, alpha-tested shadow casting, or temporal caching. A shadow-casting spotlight adds one depth-only submission for every opaque mesh instance; this bounded design is intended for a few shadowed spots, not dozens. Point shadows use an independent two-cubemap budget and six depth passes per selected light, as described below.

The opt-in `--scene-spot-shadows` GPU scenario exercises the production `SceneRenderer` with bundled geometry, IBL, directional lighting/CSM, and SSAO. It checks zero/one/two/four shadow passes, depth-only caster draw counts, dynamic light transform and bias changes, persistent resource generation, HDR target resize, shadow-slot reassignment, overflow, and spotlight-only rendering with the directional light removed. This is command/resource validation only: the current harness does not read depth or final color pixels, so visual shadow quality still needs interactive editor acceptance.

Point-light shadows use two lazily created, persistent 512x512 D32 depth cubemaps (about 12 MiB raw), independent of the four 1024x1024 spot maps and four directional cascades. Each selected point-shadow owner renders six depth-only face passes in `+X, -X, +Y, -Y, +Z, -Z` order; its entity rotation does not rotate this omnidirectional basis. Face views use a 90-degree right-handed Vulkan zero-to-one projection, near `min(0.05, range*0.01)`, and far equal to authored range. The point-shadow pixel shader writes normalized radial depth (`distance/range`); the receiver compares that same quantity, avoiding a perspective-versus-radial mismatch. `ShadowBias` is normalized radial depth, `ShadowNormalBias` is a world-unit normal offset, and `ShadowSoftness` is a bounded angular PCF radius derived from cube texels. Cube-direction sampling crosses face boundaries; exact seam/appearance quality still requires visual inspection.

The point-shadow budget is two of the camera-relevant selected 32 local lights with `CastShadows` enabled, positive intensity, valid projection, and scene casters. Eligible excess point lights remain directly illuminated but unshadowed. Selection is recomputed from current eligibility and relevance each frame with deterministic UUID tie-breaking; physical slots are retained only for owners still in the selected top-two set. The two point slots are independent of the corrected four-spotlight allocation. Worst case is twelve additional depth passes per frame when both point maps and all four spot maps are active, in addition to the four directional cascade passes; all eligible meshes are submitted to each face without spatial culling. Point maps are reused when owners change. The OpenGL bootstrap backend does not render scenes or point shadows.

GPU validator mode `--scene-point-shadows` exercises zero/two owners, all six face passes, transform and Cast Shadows changes, reassignment, mixed directional/spot/point shadows, persistent map generation, and output resize. It reports pass/draw/owner evidence but does not perform pixel readback; the dedicated [`PointLightShadows` project](../Samples/VisualValidation/PointLightShadows/README.md) is required for visual acceptance.

An opt-in GPU regression executable is available with `-DPULSEFORGE_BUILD_GPU_VALIDATION_TESTS=ON` when a Vulkan renderer configuration is enabled. For example:

```powershell
cmake -S . -B Build/CMake/VS2022-x64 -G "Visual Studio 17 2022" -A x64 -DBUILD_TESTING=ON -DPULSEFORGE_BUILD_GPU_VALIDATION_TESTS=ON
cmake --build Build/CMake/VS2022-x64 --target PulseForgeGpuValidation --config Debug --parallel 1
.\Build\CMake\VS2022-x64\Debug\PulseForgeGpuValidation.exe
```

Run it from a logged-in Windows desktop session. The default mode validates RGBA16F target draw/sample/presentation. `--scene-hdr` exercises actual HDR scene rendering with PBR meshes, HDR environment, directional shadows, and SSAO, including reuse/resize and empty/environment-only/geometry-only/directional-only cases. `--scene-tonemap` runs the real HDR scene through the shared tonemapping path to the swapchain and to sRGB and UNORM offscreen targets, changes exposure, changes extent, samples the SDR output, and covers environment-only, geometry-only, empty, and directional-only snapshots. `--editor-ui-unorm` validates alpha-blended rendering into an sRGB UI intermediate, sampling/encoding into an UNORM offscreen output, same-size reuse, resize recreation, and binding refresh. `--scene-local-lights` covers mixed local-light scene submission and active-light updates. `--scene-spot-shadows` covers actual spotlight depth passes and bounded map reuse/reassignment. The validator does not read back pixels, so it validates GPU resource creation, pipeline compatibility, transitions, and executed draw paths but not exact stored radiance or curve output values. Khronos and NVRHI validation are enabled automatically in Debug when available. The executable is not registered with default CTest, so CPU-only tests do not require a Vulkan device or display.

For manual visual review, inspect the bundled validation scene under bright and dim environments with reflective metallic and rough materials; compare positive/negative exposure; exercise directional shadows, SSAO and moving geometry; resize/minimize/restore; switch Edit/Play/Stop and projects/scenes; inspect empty-scene fallback, editor icons, fonts, and theme colors. Automated frame submission does not replace those visual checks.
